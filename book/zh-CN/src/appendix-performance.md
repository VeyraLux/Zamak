# 附录 B：性能

Zamak 经由 C 编译，所以写得好的 Zamak 代码运行速度与 C 相当。这篇附录给出实测结果，说明 Zamak 的安全检查在哪里花时间、编译器怎样去掉它们，并给出写出高效代码的建议。

## 实测结果

仓库里的[对比测试](https://github.com/VeyraLux/Zamak/tree/main/bench/compare)在同一台机器上用七种语言运行同样的程序。运行时间，单位毫秒（越小越好）：

| 程序 | Zamak | C | Rust | Go | Java | Node.js | Python |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| n-body | 167 | 158 | 112 | 183 | 332 | 326 | 15,514 |
| spectral-norm | 174 | 172 | 187 | 238 | 642 | 428 | 37,751 |
| fannkuch-redux | 185 | 190 | 194 | 203 | 390 | 321 | 10,463 |
| binary-trees | 273 | 864 | 963 | 466 | 378 | 380 | 2,510 |
| 素数统计 | 183 | 504 | 184 | 513 | 642 | 302 | 8,499 |
| 词频统计 | 137 | 122 | 190 | 190 | 658 | 816 | 785 |

hello world 只有 56 KB，启动用时 16 毫秒，占用 3.7 MB 内存，与 C 基本一样。测试方法、机器配置和复现步骤见对比测试的 README。

## 安全检查的开销

Zamak 检查整数溢出、除以零和列表下标。每次检查只是一次比较加一个极少走到的分支，但在紧凑的循环里，它可能妨碍 C 编译器做向量化或重排代码。编译器会去掉能证明多余的检查：

- **区间分析**跟踪整数可能的取值。在 `for i in range(len(xs))` 里，只要 `xs` 的长度在循环中不变，它就能证明 `xs[i]` 不会越界，于是直接访问元素。
- **常数除数**不需要检查除以零；除以 2 的幂会变成移位。
- **不会溢出的小整数**（例如不超过列表长度的循环计数器）用普通的算术运算。

## 让热点函数更快

热点函数里的整数运算编译器无法证明安全、而回绕又可以接受时，给它标上 `@wrapping`。在 spectral-norm 测试里，这一行把程序从约 340 毫秒缩短到 174 毫秒：

```zamak
@wrapping
fn a(i: i64, j: i64) -> f64:
    1.0 / ((i + j) * (i + j + 1) // 2 + i + 1)

fn main():
    println(a(1, 2))
```

```text
0.125
```

其他建议：

- **借用而不是复制**：参数用 `&[T]`、`&string`、`&Point`，没有任何开销；避免在循环里 `copy`。
- **需要下标时，按列表长度遍历区间**：`for i in range(len(xs))` 让编译器能去掉下标检查。
- **用字面量或 `push` 构建列表**：列表字面量只分配一次内存，释放的小列表会被复用。
- **用惯用写法计数**：`m[k] = m.get(k, 0) + 1`，Zamak 会把它变成一次查找。
- **直接遍历 `text.words()` 或 `text.lines()`**：只要 `text` 在循环里不变，Zamak 就直接在原文上扫描，不复制每个词。

## 查看生成的 C 代码

要准确看到 Zamak 生成了什么，把 `ZAMAK_DUMP_C` 设成一个目录：

```sh
ZAMAK_DUMP_C=out zam build app.zm
```

`zam` 会把每个模块的 C 文件写到 `out` 里。像 `add(a, b)` 这样的调用是带检查的加法，`at…(list, i)` 是带检查的下标访问；直接写出的 C 运算符，说明编译器证明了检查是多余的。
