# 常见算法性能优化

目标是在明确列出的算法、输入和工具链下，逐项改善 Zamak 相对 Rust release 与 Go 的运行性能。没有有限基准能够证明“所有常见算法”均领先；未测量的算法不在结论范围内，记录未达标项目。

## 工具链

测试环境已验证 Rust 1.96.0、Go 1.26.4、MinGW GCC 16.1.0 和 MSVC Build Tools 可以编译并运行测试程序。Windows 默认使用 MSVC；设置 `CC=gcc` 可使用 GNU 后端。编译器身份、编译选项与生成 C 均参与原生缓存键。

## 当前实现

GNU 风格后端采用 C11、`-O2 -funroll-loops`；MSVC 保持 `/O2`。循环展开已通过本机 GCC/MSVC 双后端回归及七项性能验收，尚未单独验证 Clang 的性能收益。GCC/Clang 通过 `__builtin_add_overflow`、`__builtin_sub_overflow`、`__builtin_mul_overflow` 实现有符号整数检查，其他编译器保留可移植检查。程序中的溢出、除零、`INT64_MIN / -1` 和数组越界仍然报错。除法或取余的右侧若是既非 `0` 也非 `-1` 的整数字面量，后端直接生成 C 运算；这些除数对任意 `i64` 分子都不会触发上述错误，操作数仍按原顺序求值。

除法/取余还在 GCC/Clang 下加入操作数均落在 `0..=UINT32_MAX` 时的无符号 32 位快路径；负数或更大值走原有有符号 64 位路径，除零及极小值错误先检查。跨符号与位宽边界的变量除法测试已在两个后端通过。除法相关复测结果如下，单位为毫秒/批；每个配置五个正式样本，精确校验和一致。

## 复现

在仓库根目录使用已有工具链执行：

```powershell
$env:CC = 'gcc'
pwsh -File tools/bench-common.ps1 -CCompiler gcc
```

脚本先构建 release 编译器，再分别编译对照程序。结果保存到本地 `results/tutorial-perf-*/results.json`。不要与构建、测试或其他耗 CPU 的任务并行运行。Windows 默认后端与 GNU 后端的数字分别记录，不能混用为同一次比较。

对照实现的源码不需要另行分发：Zamak、C、Python、Rust 四种驱动程序都由已入库的 `tools/common-kernel.py` 按同一份规格确定性生成，落到当次 `results/tutorial-perf-*/` 目录。重跑同一版本即可得到同一份源码，因此本页任何计时数字都可以连源码一起复现，而不是只给结论。

Zamak 是"生成 C 再交给 C 编译器"的路线。运行时间不含构建，但**构建时间必须包含调用 C 编译器的那一步**：本页只报程序运行时间，不报编译时间，也不把两者合成一个数。编译时间见 `docs/ENGINEERING.md` 与 README 的构建章节，它们记录的是完整流程（前端 + 生成 C + MSVC/gcc），不与这里的运行时间相加或相比。

## 比较方法

主对照采用 Rust `opt-level=3`、关闭溢出检查，以及 Go 默认优化构建。带溢出检查的 Rust 单独记录，用于分析语义差异。C 编译器与选项单独记录。各语言执行相同算法与种子输入，核对精确校验和；构建时间排除在程序耗时之外。

扩展基准覆盖最大公约数、素数计数、迭代斐波那契、64 项数组插入排序、64 项数组二分查找、整数算术求和、模递推。Zamak、C、Python、Rust release、带溢出检查 Rust 与 Go 的七项种子循环校验和全部一致（42 组）；正式计时使用五个样本，每次至少 0.5 秒，按固定随机顺序交错执行各语言。Zamak 的重复次数写入生成驱动程序，其他语言从命令行读取，因此循环边界可见性并不完全一致；算术求和可能被优化为闭式表达式，这属于主对照的合法优化；本基准比较源程序结果与优化后的耗时，不要求每种语言执行相同数量的机器指令。二分查找各个种子的结果均为 2080，因此精确校验和验证结果一致，不能单独证明循环未被优化消除。首轮结果如下，单位为毫秒/批。五个样本的中位数仅描述本机本次运行；接近的差异需要复测确认。

## 峰值内存

峰值内存是独立指标，单独测量、单独成表，不与耗时混排。数据来自 `results/tutorial-perf-20261012-175725-649953/results.json`，是 GNU 后端批次（`CC=gcc`），与同一台机器、同一工具链的耗时批次一并产生。与其他批次一样，这些数字只在同批内可比。

| 语言 | 峰值工作集（MiB） |
| --- | ---: |
| Zamak | 3.5 |
| C（O2） | 3.5 |
| Rust release | 3.6 |
| Rust（带溢出检查） | 3.6 |
| Go | 5.1 |
| Python | 17.4 |

每个数字是该语言七个内核（最大公约数、素数计数、迭代斐波那契、插入排序、二分查找、算术求和、模递推）中的最大值。本批七个内核在每个语言内部几乎恒定——Zamak 与 C 的七项全部为 3.5 MiB——因此只报每语言一个值，不逐内核列表。

指标定义：读取每次计时进程运行期间由操作系统维护的**整进程工作集高水位线**（Windows 用 psapi `GetProcessMemoryInfo` 取 `PeakWorkingSetSize`，其他平台读 `/proc/<pid>/status` 的 `VmHWM`）。高水位线由内核维护，只要在进程退出前成功读到一次即为真实峰值，**与轮询间隔无关**。它包含语言运行时与分配器的基线占用，不是算法本身的堆分配量。

**可以读的：** 本轮 Python 的 17.4 MiB 明显高于其余五个实现，差距远大于本方法的分辨能力。

**不能读的：** 不能据此说"Zamak 比 X 省内存"。三个编译语言（Zamak、C、Rust）落在 3.5–3.6 MiB，差异小于本方法的分辨能力，视为不可区分；这七个短程序的常驻规模主要反映各语言最小可执行程序的运行时与分配器基线，不反映算法的内存复杂度，也不能外推到更大输入或其他平台。

早期一份本地记录曾把 Zamak 的峰值内存记为 141.6 MB 并据此声称"内存最低"。该数字与同批次的耗时和 Python 的 17.4 MiB 互相矛盾，几乎可以确定是量错了进程——测到的是 `zam.exe` 编译器，而不是被计时的程序。本轮按上述定义重测，Zamak 与 C、Rust 同为 3.5–3.6 MiB，旧的 141.6 MB 结论作废。

## 这些数字说明什么、不说明什么

本页的定位是**方法记录与自相对趋势**，不是语言排名。下面把边界写清楚，避免被读成判决。

**说明的：**

- 在列出的一台机器、一组工具链、七个整数算法上，同一份规格的实现各自用 release 优化构建时的相对耗时。
- 改动前后 Zamak 自身的趋势（本页按批次分开记录，同批可比、跨批不可比）。
- 每项的离散度（median ± MAD）与校验和一致性，即这些样本是否稳定、结果是否正确。

**不说明的：**

- **不说明语言之间的普遍快慢。** 七个短程序、单机单批次，不能外推到其他算法、输入规模、平台或编译器版本。这里的对照是"这几份具体实现"，不是"这些语言"。
- **不说明编译速度。** 运行时间与编译时间是两个独立指标，本页只报前者，任何"比 X 快 N 倍"的说法都不允许把两者相乘或相加。
- **不说明 Zamak 可以脱离 C 编译器。** Zamak 生成 C，运行前仍要由 MSVC 或 gcc 构建；因此 Zamak 的"编译时间"天然包含一次 C 编译器调用，这在与其他语言比构建速度时是必须披露的前提。
- **不说明不存在更快的写法。** 每种实现都按同一算法编写，未做针对性手工优化；换个写法或换套库，结论可能改变。
- **不说明内存与二进制体积。** 峰值内存见上一节 `## 峰值内存` 的独立表，二进制体积尚未测量；这两项都单独测量、单独成表，不与耗时混排。
- **不说明浮点、字符串/正则库、多线程与任意精度场景。** 本页刻意只覆盖整数算法；缺失的语言特性不该被包装成性能差异。

**读表约定：**

- 差异小于 MAD 量级的项视为本轮不可区分，需复测才能判断方向（例：模递推 Zamak 对 C）。
- 绝对值只在同一批次内比较；跨批次只看方向与量级。
- 不把七项聚合为单一"Zamak 是 N 倍"数字——聚合会掩盖逐项的方向差异（例如 C 在二分查找、算术求和、模递推三项更快）。
- 输了就说明原因（对照实现更成熟、优化器更擅长该形状、Zamak 缺某特性），而不是换个基准重测到赢为止。

方法学依据与外部对照（各语言发布时实际公布什么、哪些案例不公平）见 [BENCHMARK-CASE-RESEARCH.md](BENCHMARK-CASE-RESEARCH.md)。
